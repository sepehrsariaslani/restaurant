# طراحی فاز اول POS آفلاین و همگام‌سازی سفارش

تاریخ: 2026-08-31

## هدف و محدوده

POS مدیریت باید پس از دست‌کم یک بار بارگذاری موفق آنلاین، در قطع اینترنت قابل بازشدن و قابل استفاده برای ثبت «سفارش عادی بدون پرداخت» در حالت بیرون‌بر و ارسال باشد. سفارش‌ها به‌صورت پایدار در IndexedDB نگهداری و با بازگشت اتصال، بدون اقدام اپراتور به‌ترتیب به Frappe ارسال می‌شوند.

این فاز شامل سفارش میز، پرداخت، تسویه، اعتبارسنجی پرداخت، تغییر قیمت/محصول، موجودی قابل‌ویرایش یا حسابداری آفلاین نیست. همهٔ این عملیات هنگام قطع اینترنت با پیام روشن مسدود می‌شوند.

## انتخاب معماری

سه مسیر بررسی شد:

1. localStorage برای داده و صف سفارش: ساده، اما برای snapshot و صف پایدار بزرگ قابل اتکا نیست.
2. Service worker برای دادهٔ کسب‌وکار: با کش HTTP و درخواست‌های POST ناسازگار و مستعد نمایش دادهٔ کهنه است.
3. IndexedDB برای دادهٔ POS و صف سفارش، همراه با service worker فقط برای پوستهٔ برنامه: انتخاب پذیرفته‌شده. این راه مرز روشنی میان دادهٔ کسب‌وکار و کش رابط ایجاد می‌کند.

## اجزا و مسئولیت‌ها

### ذخیره‌ساز POS

`frontend/src/utils/posOfflineStore.js` مرجع محلی داده‌هاست و شامل snapshot بوت POS، کش مشتری‌ها و `order_queue` است. هر سفارش صف‌شده دارای `client_order_key`، payload، زمان ایجاد، شمارندهٔ تلاش، وضعیت و خطای آخر است.

وضعیت‌ها:

- `pending`: آمادهٔ ارسال یا قابل تلاش مجدد پس از خطای موقت.
- `syncing`: فقط وضعیت نمایشی در حافظه؛ در IndexedDB به‌عنوان pending باقی می‌ماند تا قطع ناگهانی باعث گم‌شدن سفارش نشود.
- `needs_attention`: خطای تجاری یا اعتبارسنجی سمت سرور؛ تلاش خودکار متوقف و رکورد حفظ می‌شود.

### اتصال به POS

در بارگذاری صفحه، دادهٔ cache بلافاصله خوانده می‌شود. پاسخ موفق API آنلاین همان state موجود را به‌روزرسانی و سپس snapshot و مشتری‌ها را ذخیره می‌کند. اگر درخواست شبکه ناموفق باشد، POS از snapshot استفاده می‌کند و تازگی cache را اعلام می‌کند. در اولین استفاده بدون snapshot، صفحه پیام می‌دهد که ابتدا یک بار اتصال لازم است.

هنگام ثبت سفارش بدون پرداخت، تنها حالت‌های `takeaway` و `delivery` در قطع اینترنت به صف می‌روند. سفارش میز، پرداخت و تسویه پیش از فراخوانی API رد می‌شوند. ثبت آفلاین سبد را مانند ثبت موفق خالی می‌کند، اما پیام آن صراحتاً «ذخیره آفلاین شد» است و موفقیت مالی را القا نمی‌کند.

### موتور همگام‌سازی

`frontend/src/utils/offlineSyncEngine.js` سفارش‌های pending را بر اساس زمان ایجاد و فقط یکی‌یکی ارسال می‌کند. این موتور در رویداد `online` و پس از بوت موفق آنلاین اجرا می‌شود و امکان تلاش دستی نیز دارد.

- پاسخ موفق (`created` یا `existing`) سفارش را از صف حذف می‌کند.
- قطع ارتباط، timeout و خطاهای موقت، سفارش را pending نگه می‌دارد و خطا/تعداد تلاش را ثبت می‌کند.
- پاسخ‌های اعتبارسنجی یا قوانین کسب‌وکار (از جمله قیمت/موجودی تغییرکرده) سفارش را `needs_attention` می‌کند؛ حذف یا بازنویسی خودکار ممنوع است.
- اجرای هم‌زمان ممنوع است تا ترتیب صف و idempotency حفظ شود.

### API سمت سرور

از API موجود `restaurant.api_pos_reliability.replay_offline_pos_order` استفاده می‌شود. این API کلید را نرمال‌سازی می‌کند، سفارش موجود با همان `restaurant_pos_client_order_key` را برمی‌گرداند یا یک Sales Order عادی می‌سازد و همان کلید را در تراکنش ثبت می‌کند. بنابراین retry هیچ سفارش یا فاکتور تکراری ایجاد نمی‌کند.

فیلد و patch مربوطه باید پیش از انتشار با `bench migrate` اعمال شده باشد. payload آفلاین همان ساختار `createPOSOrder` است و هرگز شامل نتیجهٔ پرداخت یا تسویه نیست.

### رابط کاربری و PWA

نوار وضعیت POS چهار حالت را شفاف نشان می‌دهد: آنلاین، آفلاین، درحال همگام‌سازی و تعداد سفارش‌های در انتظار/نیازمند بررسی. یک دکمهٔ «همگام‌سازی» برای تلاش دستی دیده می‌شود؛ جزئیات خطای موارد نیازمند بررسی در دسترس اپراتور است.

Service worker فقط navigation موفق POS و assetهای رابط را cache می‌کند. درخواست‌های POST API نه cache و نه جعل پاسخ می‌شوند؛ دادهٔ کسب‌وکار صرفاً از IndexedDB خوانده می‌شود.

## خطا، تعارض و امنیت

تعارض‌های قیمت، موجودی، اعتبار مشتری یا قانون کسب‌وکار به `needs_attention` می‌روند. هیچ سفارش یا پرداختی silent overwrite یا حذف نمی‌شود. فقط داده‌هایی که همین حالا به کلاینت مجاز POS داده می‌شوند cache می‌شوند؛ توکن جلسه، رمز، CSRF یا راز پرداخت ذخیره نخواهد شد.

## آزمون و پذیرش

- آزمون واحد store: نرمال‌سازی فارسی، جست‌وجوی مشتری، پایداری صف و انتقال به needs_attention.
- آزمون موتور sync: ترتیب ارسال، جلوگیری از اجرای موازی، حذف پاسخ created/existing و طبقه‌بندی خطاها.
- آزمون transform/source برای اتصال POS، نمایش شمارش‌ها، مسیر fallback cache و عدم queue پرداخت/میز.
- آزمون API سمت سرور برای idempotency و اعتبارسنجی کلید؛ در محیط دارای Frappe اجرا می‌شود.
- بررسی build و تست‌های موجود frontend.

## شرایط انتشار

پیش از فعال‌سازی باید `bench migrate` اجرا، frontend ساخته، cacheهای Frappe پاک و terminalهای POS یک بار refresh شوند تا service worker جدید فعال شود.
